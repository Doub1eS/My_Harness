## 0. 先想清楚:这份文档回答什么问题

你手里有一份很完整的六支柱 spec(来自 Qoder/SQL 数仓场景:协调者 + 需求拆解/方案/SQL/测试四专家,钉钉提醒、状态机、SKILL 市场)。它描述的是**别人做好的成品长什么样**。

你真正的问题是:**"我自己能不能一步一步把它搭出来,并长出一个适配激光助手的形态?"**

所以本文档做的事:
1. 把六支柱**去场景化**(去掉 SQL、钉钉、数仓),抽象成一组通用组件;
2. 给一条**从零到可运行的递进学习路线**(阶段 0 → 5);
3. 留一章**激光助手试点预案**,只标假设、不展开 —— 等通用框架跑通后再逐个验证。

### 0.1 一个贯穿全文的比喻

把一次"Agent 干活"想成开车:

- **引擎/车** = 大模型 + 工具调用能力(Qwen3.8-27B + SGLang);
- **方向盘/油门** = Agent 的自主决策;
- **harness(缰绳/马具)** = 那套让"马"不跑偏的约束:往哪条路走(编排)、每段怎么喂料(context)、哪里必须停车检查(gate)、熄火后从哪重新发动(recovery)、每次跑偏记一笔下次绕开(evolution)。

harness 的价值不是"让模型更聪明",而是**让单次模型能力之外的东西被制度化**:流程、边界、验收、记忆、恢复。

### 0.2 为什么先通用、后激光

- 激光助手现在是一套**纯函数流水线**(`laser_qa`:摄取→索引→检索→生成),且在线栈是 **vLLM 35B**,与你的 harness 基座 **Qwen3.8-27B + SGLang** 不是同一个栈。
- 如果一上来就"给 laser_qa 加个协调者",你会被 35B/vLLM/防幻觉红线的存量逻辑绑架,学不到 harness 本身。
- 所以:**独立实验、后期带回**。学习期 harness 与 laser_qa 互不依赖;跑通了,再把编排/门禁/进化这些**理念**(不是代码)移植回 laser_qa 的后期迭代。

## 1. 术语表(先统一语言)

| 术语 | 含义(本文档口径) |
|---|---|
| **Harness** | 约束并驱动 Agent 完成任务的运行时层:身份定义、编排、上下文供给、门禁、状态追踪、经验沉淀。不是模型,不是单个 Agent。 |
| **Agent(协调者/专家)** | 一个"角色定义 + 模型循环 + 一组允许调用的工具"。专家只在自己领域干活;协调者只调度不产内容。 |
| **角色文件(Identity)** | 描述"这个 Agent 是谁、负责什么、能/绝不能做什么"的结构化文件,启动时加载成 system prompt。 |
| **Spec 文件** | Agent 之间传活的**结构化落盘文件**(不是对话历史)。可追溯/可审计/可恢复/可解耦/可隔离。 |
| **CP 摘要(Checkpoint)** | 每个阶段结束时,把整段过程强制压成几行固定格式,追加进状态文件,作为给下游的交接。 |
| **Phase 文件** | 每跑一个阶段才读的那个阶段的说明文件,上下文只装当前需要的。 |
| **门禁(Gate)** | 关键节点"过不过得了"的检查:自动格式校验优先,人工 checklist 兜底。 |
| **状态机** | 任务生命周期的一组枚举 + 当前停在哪个 + 流转记录(时间/原因)。 |
| **错误记录(经验本)** | 四列表:|序号|日期|一句话错误|正确做法|。是进化的燃料。 |
| **O + S** | Orchestrator(协调者)+ Specialist(子专家)架构。 |

## 2. 技术基座

**结论先行:阶段 0 的唯一目标是"让一个 Qwen 模型能自主多轮调用工具并基于结果作答",其余全部建立在这个循环之上。**

### 2.1 基座栈

- **模型**:Qwen3.8-27B(可考虑 FP8 量化),本地 SGLang 起服务。
- **服务**:SGLang 的 OpenAI 兼容端点(参考你已在 aux_assistant 用过的 :8003)。
- **关键参数手法**:Qwen 的 thinking 通过 `extra_body={"chat_template_kwargs": {"enable_thinking": bool}}` 控制(这是 SGLang qwen parser 的方式),与 laser_qa 的 ollama `/api/chat + think:false` 不同。

### 2.2 唯一可复用代码种子:`aux_assistant/llm.py`

你已经在 `Laser_assistant/aux_assistant/` 里验证过最关键的循环,这是**起点不是终点**:

- `QwenClient.complete(messages, tools=...)`:单轮补全,带 tools;
- `QwenClient.run_tools(messages, tools, execute, max_rounds, on_event)`:**模型自主多轮调工具**,直到给纯文本答案 —— 这就是 harness 的引擎;
- `reasoning_of()`:读 SGLang 的 `reasoning_content`。

> **学习要点**:`aux_assistant` 已经证明"27B + 工具循环"可用,但它只有一个角色(找说明书)、一组写死的工具、没有编排/门禁/状态。harness 要做的,是把这段循环**参数化、分角色、加治理**。

### 2.3 独立性红线

学习期 harness 独立成工程(建议 `~/MyHarness/harness-lab/` 或独立仓库,**不放进 Laser_assistant 目录**),不 import `laser_qa` 业务代码、不与 :8002 vLLM 竞争。理念后期才带回。

## 3. 支柱一 · Identity(身份层)→「角色文件 + 约束金字塔」

### 3.1 问题

要求里说"每个 Agent 的能力定义很薄,反而稳"。为什么薄能稳?因为**边界是声明出来的,不是靠模型自觉**。如果"你是检索助手"这句话淹在 2000 字里,模型就守不住。

### 3.2 通用落地:一个 Agent = 一个目录

```
roles/
  coordinator/                # 协调者:只调度、把关、评审、汇报
    identity.md               #   我是谁/负责什么/绝对不负责什么
    io.md                     #   输入输出格式(结构化 schema)
    constraints.md            #   行为约束(三层金字塔,见 3.4)
  specialist_a/               # 某个领域专家
    identity.md
    io.md
    constraints.md
  ...
```

设计要点:

1. **identity.md 强制写"不负责什么"**:这是能力边界最有用的部分。"我是检索助手,不负责改写用户问题、不负责判断方案对错。"
2. **io.md 决定 Agent 之间怎么传活**:输出必须是结构化 spec(JSON 或固定模板),不是自由对话。这是"Spec 文件驱动"(支柱三)的身份层根基。
3. **能力说明 = 允许调用的工具白名单**:每个专家只挂自己领域的工具,协调者不挂任何产出工具(只能调"派活/评审/汇报"这类元工具)。

### 3.3 协调者的 6 身份怎么收敛

要求里协调者叠了 6 个身份(调度/澄清/审查/门禁/汇报/重试)。通用落地:**不是做 6 个 Agent,而是把协调者的一段 system prompt 按 6 个职责拆成 6 个"角色块",每次只激活当前该有的块**。比如:

- 收到需求 → 激活「澄清员」块 + 「调度员」块;
- 专家交活 → 激活「审查员」块 + 「门禁员」块;
- 出错 → 激活「重试员」块。

这同时呼应支柱三的渐进加载:上下文里永远只放"现在这一步"需要的身份定义。

### 3.4 行为约束三层金字塔(最重要的设计)

要求里把约束分三层,理由是**"规则太多,Agent 会选择性遵守"**。通用落地为一个模板:

```
constraints.md
├── ⛔ 超级红线(≤7 条,每条"违反=事故",置顶、单独高亮)
│     · 禁止跳过阶段切换的用户确认
│     · 禁止编造:工具/知识库没返回就直说没有
│     · 禁止越界:只做自己 identity 声明的事
│     · ...
├── 📕 错误记录(历史踩坑,启动时加载,见支柱六)
│     · |2026-09-01| 上个月在 X 场景跳过上传 | 必须先落 spec 再进下一阶段|
├── 📋 操作规则(流程/模板/标准做法 —— 大量,按需渐进加载,不全塞)
```

**关键机制:三层的加载策略不同。**

| 层 | 何时加载 | 为什么 |
|---|---|---|
| 超级红线 | 每次启动都加载,永远在上下文最前 | 少,重要,必须脱颖而出 |
| 错误记录 | 每次启动加载,放在红线后 | 让 Agent"以前在这栽过,注意" |
| 操作规则 | 只在跑对应阶段时加载(支柱三) | 多,不能稀释注意力 |

### 3.5 归属阶段

身份层在**阶段 1** 建最小版(角色文件 + 加载器),阶段 2 起随协调者/专家演化。

## 4. 支柱二 · Orchestration(编排)→「流程声明 + 路由」

### 4.1 问题

要求里:链路/快案/快码/单点、输入自动识别、无依赖并行、修改分级。这些都是**具体流程**,通用化后只剩两个组件。

### 4.2 通用落地

**(a) 一次任务 = 一个 DAG(阶段图)**

把任何任务都描述成"一组有序阶段,有些可并行":

```
RECEIVE → ANALYZE → (PLAN → REVIEW) → EXECUTE → TEST → DELIVER
                     ↑ 可并行子分支
```

- 全链路/快案/快码在通用框架里**不是三种特殊实现**,而是**同一个 DAG 的三种裁剪**:从 ANALYZE 前砍掉、从 PLAN 前砍掉…… 用一个 `start_at` 参数表达。
- 单点模式 = DAG 只有一个节点。

**(b) 路径选择 = 一个路由函数**

```python
def route(input_text) -> PathSpec:
    # 规则匹配,不是让模型猜:输入是"链接/长文档/PRD"还是"一句话/口头需求"
    # 返回 (dag, start_at)
```

要求里"用户贴的是链接还是自然语言,不让用户选输入类型"——通用化为**输入分类器**:用规则(URL 前缀/长度/关键词)先分输入形态,再映射到路径裁剪。

**(c) 并行 = 明确声明依赖**

每个阶段的 spec 文件声明它依赖上游哪些 spec 文件。**没有依赖 → 可以并行**;实现上每个专家是独立会话(Sub Agent 隔离,见 5.5 红线),天然可并发。

**(d) 修改分级 = 一个"改多少"的判断**

| 级 | 例子(域无关) | 做法 |
|---|---|---|
| 轻量 | 改名/注释/格式 | 主 Agent 直接动手,不派专家 |
| 中等 | 逻辑调整 | 派专家 + 一份精确修改点清单 |
| 重大 | 架构性变更 | 重走完整 DAG |

### 4.3 归属阶段

阶段 0(单循环)、阶段 2(协调者 + 2 专家的最小 DAG + 路由)起步;并行与修改分级作为阶段 2 的进阶项。

## 5. 支柱三 · Context(上下文工程)→「目录结构 + CP 摘要 + 渐进加载」

### 5.1 问题

要求四条:阶段切分、摘要替代全文、渐进加载、Spec 文件驱动。它的**总原则**是:**不要一锅端,别把整段对话喂给每一步。** 这也正是 27B 长上下文吃紧时最该先做的工程。

### 5.2 通用落地:一次任务一个工作目录

```
runs/<task_id>/
  task.md            # 原始需求(不变的根)
  state.json         # 状态机(支柱五)
  cp.md              # CP 摘要:每阶段结束追加几行
  specs/             # 各阶段产出 spec 文件(传活用)
    analyze.md
    plan.md
    result.json
  logs/              # 原始对话留档(不进上下文,只可回溯审计)
```

**(a) Spec 文件驱动** = 阶段间唯一的信息传递通道。专家 A 的产出落在 `specs/analyze.md`,专家 B 启动时只读这个文件,**不读 A 的对话**。好处:可追溯(每决策能找到出处段落)、可审计、可恢复、可解耦(下游不关心 A 怎么想的)、可隔离。

**(b) CP 摘要** = 每阶段结束强制压缩成固定格式追加进 `cp.md`:

```
## CP-<阶段名>-<时间>
结论:<一句话>
传递给下游的关键信息:<类型=…/关键参数=…>
待关注事项:<…>
```

下游读到这 5 行就明白上游做了啥,不需要回溯几十轮对话 —— 27B 下这是刚需不是优化。

**(c) 渐进加载** = 一个 Agent 的角色文件分"核心层 + 详情层":

- 核心层(必读,常驻):红线一句话摘要 + 文件路由表(哪个阶段读哪个文件)。
- 详情层(按需):只有"这一步涉及哪类规则"才加载对应的那条。

### 5.3 归属阶段

阶段 0/1 先不搞(单阶段不需要);**阶段 4** 集中落地 phase 切分 + CP 摘要。但 5.2 的 runs/ 目录从阶段 2 起就建立。

## 6. 支柱四 · Gate(门禁)→「check 函数 + checklist + 评审分离」

### 6.1 问题

要求核心:**"取消 AI '我觉得不需要检查'的权力"** —— 用制度对抗"模型觉得差不多就行"。以及生成评估分离(自己不能既当运动员又当裁判)。

### 6.2 通用落地

**(a) 门禁点(域无关的一串固定检查)**

| 门禁点 | 检查内容 | 自动/人工 |
|---|---|---|
| 上游产物存在性 | 进下一阶段前,上游该产出的 spec 文件是否齐全 | 自动 |
| 结构校验 | spec 是否符合 io.md 的 schema(必填/字段/格式) | 自动 |
| 引用合法性 | 结论引用的编号/出处是否真实存在(反幻觉) | 自动 |
| 阶段切换用户确认 | 硬性 Human-in-the-loop,必须用户点头 | 人工 |
| 发布/交付前终检 | 最后过一遍 checklist | 人工 |

**(b) 硬/软分层**

- **硬性标准**:不通过就**不允许进下一阶段**(自动校验可实现);
- **软性标准**:达不到记录 warning、提示人工重点关注,但不硬卡。

**(c) 评审分离**

- 专家 = 埋头生产,不自己验收;
- 协调者 = 拿着 checklist 逐项打勾,**因为没参与生成,没有护犊子动机**。
- 具体实现:协调者的「审查员」角色块 + `checks.py`(自动校验函数)+ `checklist.md`(人工项表格,每阶段一张)。

### 6.3 归属阶段

阶段 3 落地最小集:**上游产物存在性 + 结构校验(自动)+ 阶段切换确认(人工)**。

## 7. 支柱五 · Recovery(恢复)→「状态机 + 故障三档 + 断点续接」

### 7.1 问题

要求核心:**干到哪儿记到哪儿,断了不用从头来;故障分三档,处理方式不同。**

### 7.2 通用落地

**(a) 状态机(域无关)**

通用化 SQL 那串状态为(实际以你的 DAG 为准,状态 = 阶段图节点):

```
RECEIVED → ANALYZING → ANALYSIS_REVIEW_PASSED
        → PLAN_GENERATING → PLAN_REVIEW_PASSED
        → EXECUTING → EXEC_REVIEW_PASSED
        → TESTING → TEST_PASSED / TEST_SKIPPED
        → DELIVERING → COMPLETED
```

- 存 `runs/<task_id>/state.json`;**每次状态流转都记录(时间、从哪到哪、原因)** —— 这是恢复的决策依据。
- 状态机不是摆设:它是"现在在哪个阶段 + 该加载哪个 phase + 给下游看哪个 spec"的唯一来源。

**(b) 故障三档**

| 档 | 例子(域无关) | 动作 |
|---|---|---|
| 可重试 | 工具超时、单次检索空、临时网络 | 自动重试 1–2 次 / 降级(换个工具同目标) |
| 需回退 | 专家产出没过门禁、测试不通过 | **退回上一个稳定存档点**,重派对应专家重做(不是从头) |
| 必须中止 | 需求理解根本性偏差、依赖装不上、多轮检索失败 | 停下来坦诚告诉用户"我搞不定,需要你帮忙" |

**(c) 断点续接**

故障恢复靠两样东西都在文件里(支柱三/五):
1. `state.json` → 判断退到哪个状态;
2. `specs/` 上游产出 → 重派专家时知道给他看什么。

**注意**:中止档是最难也最容易被模型糊弄过去的 —— 模型倾向"硬编一个答案继续"。红线里要有:多轮失败**必须认怂**。

### 7.3 归属阶段

阶段 3(与 Gate 一起,一进一出闭环)。状态机从阶段 2 起就建立并随 DAG 维护。

## 8. 支柱六 · Evolution(进化)→「错误记录 + 自动加载 + 升级机制」

### 8.1 问题

要求四句话:结构化记录、实时触发、自动加载、约束迭代。它让系统越用越不犯错 —— 错误成为燃料。

### 8.2 通用落地

**(a) 每个专家一个"踩坑本"**(四列表,`memory/<agent>/errors.md`):

```
| 序号 | 日期 | 一句话错误 | 正确做法 |
| 1 | 2026-09-01 | 检索为空时我编了个通用答案 | 空就空,如实说"没有匹配",触发中止档 |
```

- **实时触发**:用户说"你这里做错了"的那一秒就 append(不是攒批)。
- **结构化是关键**:流水账没法检索、没法在启动时变成约束。

**(b) 自动加载**:Agent 启动时,把自己的 `errors.md` **强制**拼进 system prompt(在红线之后,见 3.4)。不靠记忆力,靠机制强制回顾。

**(c) 约束迭代(升级/降级)**:

- 反复出现的同一类错误(脚本统计触发次数)→ 说明它只是"记录"不够 → 升级成超级红线;
- 升级决策由**工程师**做,但**触发信号来自数据**(统计),不是人肉翻记录;
- 反向也成立:证明过严的红线可降级回操作规则。

### 8.3 归属阶段

错误记录最小闭环在**阶段 5**(先有完整 DAG 才有"在哪栽的");但从阶段 1 起,每个 demo 里"你错了"都要当场记一笔 —— 养成习惯。

## 9. 分阶段学习路线(最小 → 全)—— 文档核心

> 每一阶段:**目标 / 要写的文件 / 跑通判据 / 风险提示**。前一阶段产物是后一阶段输入,顺序别跳。

### 阶段 0:单 Agent + 1 个工具循环(半天)

- **目标**:证明"Qwen3.8-27B + SGLang + tools"在你机器上跑通自主多轮调用。
- **写**:
  - `lab/llm.py` —— 从 `aux_assistant/llm.py` 抄/抽离 `QwenClient`(complete / run_tools / execute 接口);
  - `lab/demo0.py` —— 一个工具(如"本地检索一个小文本库"),一段对话让模型自己决定调它。
- **跑通判据**:模型在对话中触发工具 → 拿到结果 → 基于结果给出答案;**不调工具时老老实实不编**。
- **风险**:thinking 开关是否生效;工具 schema 格式 SGLang 是否吃;多轮后 context 增长。
- **产出即引擎**:此后所有阶段复用 `run_tools` 循环。

### 阶段 1:身份层(角色文件 + 红线加载)

- **目标**:把"你是谁/能/绝不能"从代码/提示词里抽出来,变成**文件声明**。
- **写**:
  - `roles/specialist_a/{identity,io,constraints}.md`;
  - `lab/role.py` —— `load_role(name)` 把三文件拼成 system prompt(红线置顶);
  - `demo1.py` —— 同一个 `run_tools` 循环,但 system 来自角色文件。
- **跑通判据**:改角色文件不改代码 → Agent 行为改变;**role.py 是唯一入口**,说明身份已文件化。
- **风险**:io.md 写得太松 → 下游没法接;太紧 → 专家没法表达。

### 阶段 2:协调者 + 2 个专家(最小 DAG)

- **目标**:Orchestrator 路由 + 派活 + 收活,自己不产内容。
- **写**:
  - `roles/coordinator/`(6 角色块 + 约束)与第 2 个专家角色;
  - `lab/orchestrator.py` —— 实现一个两阶段 DAG(如 `ANALYZE → 由路由选 EXECUTE_A 或 EXECUTE_B`),每专家在**独立 run_tools 会话**跑,产出落 `runs/<id>/specs/`;
  - `demo2.py` —— 一次完整调度:输入 → 路由 → 专家 → spec 落盘。
- **跑通判据**:协调者只做"派谁/审/汇报",答案内容全部来自专家产出 spec;**没有一处协调者自己在写专家该写的活**。
- **风险**:协调者越界(忍不住自己产内容)—— 靠红线 + 门禁(阶段 3)兜。

### 阶段 3:Gate + Recovery(一进一出闭环)

- **目标**:专家交活要过门禁;出错能退到上一个存档点;挂了能续。
- **写**:
  - `lab/gate.py` —— 自动检查(spec 存在性 + io schema 校验)+ checklist 人工项;
  - `lab/state.py` —— `state.json` 读写 + 流转记录;
  - 在 `run_tools` 外套 recovery 层:捕获失败 → 按三档处置(重试/回退/中止认怂)。
- **跑通判据**:
  - 故意让专家产出缺字段 → **gate 拦下打回**,不进入下一阶段;
  - 中途杀掉进程 → 重启后从 `state.json` 续接,而不是从头来;
  - 连续失败 → 触发中止档,输出认怂话术(不编)。
- **风险**:回退后专家看不到"上次错哪"(需要把 gate 失败原因也写进回传 spec)。

### 阶段 4:Context(phase 切分 + CP 摘要)

- **目标**:上下文只装当前阶段要的;阶段间靠 CP 摘要交接。
- **写**:
  - 把 `roles/*/constraints.md` 拆成"核心层 + 详情层"、按阶段路由加载;
  - `lab/cp.py` —— 阶段结束把过程压成固定格式追加 `cp.md`;
  - `demo4.py` —— 拉长一个多阶段任务,观察系统 prompt 长度与交接质量。
- **跑通判据**:每阶段加载的系统内容只增该阶段所需;下游专家读 `cp.md` 5 行即可开干,不需要上游全文。
- **风险**:摘要丢关键信息 → CP 模板强制"待关注事项"字段。

### 阶段 5:Evolution + 端到端验收

- **目标**:错误能记、能加载、能升级;用**真实小任务**全链路验收。
- **写**:
  - `memory/<agent>/errors.md` + 自动加载拼接 + 触发统计脚本;
  - 把「升级/降级」做成一个可读的决策记录(哪条错误 × N 次 → 升级为红线)。
- **验收 = 学会 harness**:
  1. 只靠 27B + SGLang(不碰 35B / laser_qa 代码),跑通一个**端到端真实任务**:如"给一小批文档做检索+问答",路上经过编排、门禁、状态机、认怂、断点;
  2. 当你说"某步你错了",它能当场记一笔,并且**下一轮同一场景不再犯 / 至少能看到这条教训**;
  3. 你能用 3 句话向别人讲清每个支柱解决了什么问题(讲不清 = 还没学会)。
- **风险**:演进数据太少(跑一次没几条教训)→ 可先用"故意埋错"的任务喂错误记录。

## 10. 激光助手适配预留(试点预案 —— 只标假设,不实现)

> 通用框架(阶段 0–5)跑通后,用**真实激光场景**逐个验证以下假设。验证一个、成熟一个、再考虑移植回 `Laser_assistant`(届时才与 vLLM 35B 栈整合)。**现阶段不做任何 laser_qa 改动。**

| 支柱 | 激光场景的假设实例化(待验证) |
|---|---|
| **Identity** | 专家集合假设:`案例检索专家`(275 案例 Excel)、`资料库检索专家`(133 份文档/3876 页)、`看图 VLM 专家`(照片/缺陷)、`选型专家`(77 激光器/44 冷水机)、`参数推荐专家`(二期);超级红线假设:任何结论必须挂 CASE-XXX 出处、无匹配回固定认怂话术、未解决案例如实标注、绝密数据不上公网。 |
| **Orchestration** | /ask 一次提问 = 一个任务:判型(纯文本问 / 传图问 / 查文档 / 查案例 / 选型)→ 路由到对应专家 DAG;诊断树(阶段一·五)正好是天然的多步判别式路径。 |
| **Context** | 照片描述/扩写词条这类"已压好的中间产物"≈ CP 摘要思想的现成例子;文档页级检索 ≈ 渐进式取料。 |
| **Gate** | 检索门限(稠密 IP≥0.4 / 词法重叠≥2、RRF k=60)就是现成门禁;产出无 CASE 引用 → 打回。 |
| **Recovery** | 检索腿失败可重试/降级(视觉腿默认关就是一次"降级决策");多轮检索仍无匹配 → 中止档 = 认怂话术(现状 0.08s 即此档)。 |
| **Evolution** | feedback.jsonl(👍/👎)是**现成错误信号源** —— 目前只被监控消费,没回流成"错误记录";未来 👎 的答案可结构化进对应专家经验本。 |

**一句话**:激光助手现在最接近"六支柱里的 Gate + Recovery(防幻觉/认怂/门限)",最缺的是"Orchestration(路由) + Evolution(反馈回流)"。这决定了后期迭代的优先级假设 —— 但等你阶段 5 跑完再来校准。

## 11. 建议仓库布局 + 验收口径

### 11.1 建议布局(学习期独立工程,阶段 0 后定落点)

```
~/MyHarness/harness-lab/            # 独立实验工程(与 laser_qa 完全解耦)
├── llm.py                          # ← 从 aux_assistant/llm.py 抄来并抽离(阶段0)
├── role.py                         # 角色文件加载 → system prompt(阶段1)
├── orchestrator.py                 # 协调者:路由/派活/收活(阶段2)
├── gate.py                         # 门禁自动检查(阶段3)
├── state.py                        # 状态机存取(阶段3)
├── cp.py                           # CP 摘要(阶段4)
├── roles/
│   ├── coordinator/{identity,io,constraints}.md
│   └── specialist_*/...
├── memory/<agent>/errors.md        # 踩坑本(阶段5)
├── runs/<task_id>/                 # 一次任务的 spec/state/cp
├── checks.py                       # 各门禁点实现
├── demo0.py ... demo5.py           # 每阶段一个跑通脚本
└── README.md                       # 记你每阶段的"为什么这么做"
```

### 11.2 验收口径(什么样叫"做完了这份设计稿")

1. 按阶段 0 → 5 顺序,**每个 demo 有跑通记录**(判据见各阶段);
2. 六支柱在代码里都能指到对应文件(Identity→roles/、Orchestration→orchestrator.py、Context→runs/+cp.py、Gate→gate.py+checks.py、Recovery→state.py、Evolution→memory/);
3. 途中你必然会对这份设计稿做修改 —— **README 里记下"原设计哪里不对、我改成了什么"**,这才是学习本身;
4. 能对激光助手说出(而不是猜):它该引入协调者的**第一个真实场景**是什么。
